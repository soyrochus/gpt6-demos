# Temblor browser engine for Quake III Arena

Build **Temblor**, an open-source Quake III Arena clone in Rust under GPL-2.0-or-later. The coding agent implements, tests, and packages the game. A person opens it in a browser, controls their character with the keyboard and mouse, and plays against a bot built into the engine. The finished game runs independently of the coding agent. Deliver a static web build with a **Play** button and a redistributable arena. Also provide a local file picker for playing a supported original Quake III Arena map from the player's own game data.

**What the player can do in the first release.** From a fresh browser session, the player enters an arena, hears and sees an opponent, moves to cover, collects a weapon, aims, fires, scores a frag, gets fragged, respawns, reaches the frag limit, sees the result, and starts a rematch. The keyboard moves the player’s character. The mouse turns the view, aims, and fires. The engine applies the same movement and combat rules to both competitors. The opponent can win.

## 1. Product scope and compatibility

Ship local free-for-all with one human and at least one autonomous bot. Use a default frag limit of five. Keep the match entirely on the client after the assets load. The public demo needs no account, installation, commercial game files, application server, or developer console. The target is a desktop browser with mouse, keyboard, and WebGPU. Use Temblor as the engine name in the browser, README, and release packages. Identify Quake III Arena as the compatibility target.

Deliver two playable content paths:

- **Play the bundled arena.** Use an existing OpenArena map as the default. Start with `oa_rpg3dm2`, a retextured edition of the Quake III community level *Trial by Error*. Inspect its entity list, assets, source availability, and routes before committing to it. If its dependencies prevent redistribution, select another existing OpenArena deathmatch BSP with verified sources and record the reason. The release must play an existing, independently authored map. [OpenArena change history](https://sources.debian.org/src/openarena-088-data/0.8.8-2/CHANGES) · [Packaged BSPs](https://sources.debian.org/src/openarena-maps/0.8.5split-15/pak1-maps/maps)
- **Play an original Quake III map.** Target the unmodified retail `maps/q3dm1.bsp` from a lawfully supplied local `baseq3` installation. Let the owner select the relevant PK3 archives, resolve the map's assets across those archives, select the map, and start the same match. Exercise this path with licensed data when available. Without access, deliver the importer and executable test procedure, keep the retail acceptance row open, and identify the missing input. A pass on OpenArena establishes the public demo only. [ioquake3 player guide](https://ioquake3.org/help/players-guide/)

The product goal is an open-source Quake III Arena clone. The first playable release covers the named, tested maps and the documented free-for-all rules. Full base-game parity, execution of third-party QVM mods, Internet multiplayer, bot personality parity, mobile controls, and other game types are future releases. A locally simulated opponent makes the first release a complete game without that infrastructure.

## 2. Implementation strategy

Write the runtime map loader, collision, player movement, game rules, bot controller, and renderer in Rust. Compile the shipping runtime to `wasm32-unknown-unknown`. Use `wgpu` and WGSL for rendering. Keep JavaScript or TypeScript small and browser-specific. Running a precompiled C engine inside a Rust launcher fails the implementation requirement. A native reference executable is valuable for comparison, and native Rust tests may share the simulation. [wgpu backends](https://wgpu.rs/) · [id's GPL source release](https://github.com/id-Software/Quake-III-Arena)

**Port the required base-game rules into Rust for this release.** The engine handles movement, weapons, scoring, and bot behavior locally. Pin an id source revision. Use its shared movement and game code as the behavioral reference. Inspect ioquake3 when a modern implementation clarifies a compatibility issue. A Quake Virtual Machine interpreter would become relevant for running original mod binaries. It is unnecessary for playing a BSP with built-in Rust game rules. [Original game code](https://github.com/id-Software/Quake-III-Arena/tree/master/code/game) · [ioquake3](https://github.com/ioquake/ioq3)

Organize around four boundaries. They can begin as modules within a small Cargo workspace.

| Boundary | Responsibility | Contract |
| --- | --- | --- |
| Content | Mount archives, resolve paths, parse levels and materials, decode required media | Accept bytes from disk or browser. Return validated game data, resource origins, and actionable errors. |
| Simulation | Own match time, world state, collision, actors, items, projectiles, and score | Consume timestamped player and bot commands. Publish immutable snapshots and one-shot events. Run headlessly with a seed. |
| Presentation | Draw the world, opponent, pickups, effects, weapon, HUD, and menus. Play sounds. | Read snapshots and events. Rendering frequency and audio availability cannot change a combat result. |
| Browser host | Load packaged or selected files, create GPU surface, capture input, unlock sound, handle focus and resize | Start and stop one game instance. Destroy old resources and listeners when replacing a match or map. |

Use a fixed simulation step and a monotonic match clock. A practical starting value is 8 ms for movement commands with reference-compatible fixed movement settings. Document the chosen timing and use it on both sides of reference comparisons. Sample mouse deltas once, distribute commands by simulation timestamp, preserve button transitions, interpolate presentation, and cap catch-up after a stall. Pausing freezes match time, cooldowns, and the bot. Seed the simulation RNG for tests. Reserve events for transitions such as a shot, item pickup, frag, or respawn so interpolated frames never replay them.

## 3. Content loading and rendering

1. Implement a virtual filesystem for ZIP-based PK3 packages. Normalize virtual paths consistently and define deterministic precedence for base packages, numbered patches, and selected map packages. Keep the base-game and OpenArena configurations distinct. Show which archive satisfied a resource. Read user-selected files locally. Resolve required dependencies before starting the match and retain the current playable session if a new import fails.
2. Read little-endian IBSP version 46. Validate directory bounds, record sizes, cross-indices, finite geometry, archive paths, and resource limits before allocating from input sizes. Parse entities, shaders, planes, nodes, leaves, leaf references, models, brushes, brush sides, vertices, mesh indices, surfaces, lightmaps, and visibility data as needed. Keep Quake coordinates and units in simulation. Convert axes, triangle winding, and depth convention at a single rendering boundary. [id's disk structures](https://github.com/id-Software/Quake-III-Arena/blob/master/code/qcommon/qfiles.h)
3. Render planar surfaces, triangle meshes, and curved patches used by the selected maps. Resolve texture coordinates, lightmaps, vertex colors, culling, depth, and transparency. Inspect all material scripts actually referenced by the fixtures. Implement the stages and directives they use, including sky, animated or scrolling surfaces, and alpha-tested geometry where present. Record remaining unsupported directives with affected materials. A missing material on a fight route, hazard, or pickup must be fixed before accepting the map. [Original BSP renderer](https://github.com/id-Software/Quake-III-Arena/blob/master/code/renderer/tr_bsp.c)
4. Show an animated opponent whose pose, facing, firing, hit, and death cues are readable during play. Pickups must be identifiable and disappear when collected. Show the equipped weapon, crosshair, hit feedback, and projectile travel and impact. Use appropriately licensed models, textures, and sounds. For models drawn from the game packs, implement the MD3 frames, skins, tags, and animation configuration actually required. Render an in-match HUD with health, armor, ammo, weapon, both scores, and frag limit.
5. Build a per-map inventory from the actual BSP and mounted game data. List spawn entities, items, submodels, targets, triggers, hazards, and materials, plus how each is handled. Implement every entity that affects traversal or combat on an acceptance map. Bind inline brush models by their BSP model index. Retain diagnostics for unknown decorative entities. Test a second archive mount order and a missing dependency through the real import UI.

## 4. Player movement and arena behavior

Support mouse look, forward/back, strafe, jump, crouch, weapon selection, and firing while moving. Use Quake-style ground acceleration, friction, air acceleration, gravity, step-slide movement, and bounded player collision. Clip a swept player volume against solid BSP brushes, clip surfaces, relevant curved geometry, movers, and live actors. Use the reference contents masks for solid, player clip, trigger, and projectile interactions. A player must be able to climb stairs, slide along an oblique wall, jump a reachable gap, and stop under a low ceiling. [Reference movement](https://github.com/id-Software/Quake-III-Arena/blob/master/code/game/bg_pmove.c) · [Step and slide behavior](https://github.com/id-Software/Quake-III-Arena/blob/master/code/game/bg_slidemove.c) · [Reference collision](https://github.com/id-Software/Quake-III-Arena/blob/master/code/qcommon/cm_trace.c)

Resolve spawn position and facing from map entities. Use valid deathmatch spawn points and the reference spawn rules as the starting point. Handle occupied spawns consistently. Implement jump pads, teleport destinations, doors, platforms, damage volumes, liquids, or kill planes wherever the selected maps use them. Both actors must be able to reach fights and navigate the required routes. A wall run-through, unrecoverable fall, inaccessible necessary item, or spawn inside solid geometry is a release failure.

For movement verification, record timed user commands, the initial position, movement settings, and expected results from the reference. Compare flat acceleration, braking, jump apex and landing, stair stepping, and wall sliding at matching command times. Use explicit tolerances established on a repeated reference run. Preserve the reference output independently of the Rust implementation.

## 5. Combat, opponent, and match rules

**Weapons and pickups.** Implement the starting machinegun and gauntlet, a pickup projectile weapon such as the rocket launcher, and the additional weapons and pickups that materially affect the accepted maps. Inventory the actual item classes before budgeting them. Use reference fire intervals, ammo consumption, switching, damage, armor absorption, knockback, item availability and respawn times. The machinegun uses a line trace and reference spread. Rockets travel over time, collide with world or actor, and apply direct and splash damage with the reference visibility and self-damage rules. Validate that a solid wall blocks a shot, a miss consumes ammo, an empty weapon cannot fire, and a nearby explosion can change the outcome of a fight. [Game rules and weapon sources](https://github.com/id-Software/Quake-III-Arena/tree/master/code/game)

**Opponent.** Drive the bot through the same movement, aiming, weapon, damage, inventory, and respawn interfaces as the human. It must seek a traversable route, round an obstacle, pursue or reacquire a lost target, collect a useful item, engage within line of sight, and recover after blocked movement or death. Give it bounded aim speed, reaction delay, and imperfect aim so a human can both win and lose. Prefer a navigation graph derived from map geometry or usable AAS reachability. An offline-generated graph is acceptable if reproducible from the map and available for both accepted maps, including local imports. Never key fight behavior to the player's exact spawn or to a scripted camera route.

**Match.** A valid kill credits the attacker exactly once. Apply the selected base-game suicide and world-death scoring rules. Death disables movement and firing until respawn. Restore the correct starting inventory, health, and ammo on respawn, keeping the match score. At the frag limit, freeze scoring and display the winner and final scores. Rematch resets actors, items, projectiles, scores, timers, and input state. Implement positional or directional sound for shots and impacts, plus audible pickup, pain, death, and respawn cues. Sound must resume correctly after pause.

## 6. Browser experience and operating targets

Show **Play**, **Load local game files**, **Controls**, and access to licenses and corresponding source. Play starts the bundled match with one deliberate interaction to request pointer lock and enable Web Audio. Show loading progress and a retryable error if initialization fails. Default controls are WASD, mouse look, primary mouse fire, Space jump, C crouch, number keys or wheel to switch, Tab for scores, and Escape to pause and release the pointer. Provide sensitivity and volume controls. Handle denied pointer lock and explain how to retry. On blur, pointer-lock loss, or backgrounding, clear held inputs and pause. Resume on a new gesture. [Pointer Lock](https://developer.mozilla.org/en-US/docs/Web/API/Pointer_Lock_API) · [WebGPU](https://developer.mozilla.org/en-US/docs/Web/API/WebGPU_API)

Serve the static build from HTTPS or localhost. Test desktop Chromium with hardware WebGPU as the first supported configuration. Record actual browser version, OS, GPU, internal resolution, and device pixel ratio. Probe adapter creation and required limits before loading the full arena. An unsupported browser gets a visible diagnosis. Keep a single-threaded Wasm route available for ordinary static hosting. Further backends and browsers earn a supported label after the same gameplay tests pass.

Set a release target of median frame time at or below 16.7 ms and p95 at or below 33.3 ms at 1280 × 720 internal resolution on one named, hardware-accelerated desktop machine. Measure two minutes of active combat after warm-up with frame timestamps, then test five rematches for leaked listeners, duplicated sound, or growing live GPU resources. Report cold load time, transferred asset size, and any long stalls. Tune visibility culling, texture upload, patch tessellation, and asset packaging against measurements. Performance targets are project criteria, not measured results.

## 7. Delivery order

| Increment | What the agent delivers | Exit demonstration |
| --- | --- | --- |
| 1. Baseline | Pin source revisions, choose legal fixtures, inventory entities and dependencies, run the reference arena, and capture a route and a fight. Establish a repeatable browser build. | A clean checkout loads the fixture and records its map ID, hash, spawn count, and material dependencies. |
| 2. First playable combat | Bring up a rough rendering of an actual BSP, solid movement, one visible moving opponent, firing, damage, scoring, and respawn. A tiny source-controlled test room may support regression tests. | A person can move, aim, and frag the bot with the browser game's normal controls. The bot can frag the player. |
| 3. Complete the arena | Implement the fixture's routes, materials, pickups, differentiated weapons, audio, bot navigation, HUD, and intermission. | A player can start, finish, and restart a five-frag match from the public Play button. All essential routes and pickups work. |
| 4. Original data and import | Mount user-supplied base packages, handle missing files and material dependencies, select a named map, and build navigation. | Run the same match acceptance on retail q3dm1 with licensed data and record the outcome separately. |
| 5. Reproducible release | Package the Wasm application, free content, notices, sources, instructions, and evidence. Profile the shipping build in a desktop browser. | A fresh browser on a second clean profile can play the bundled match using only the release directory and an HTTP server. |

Build the first fight before spending time on broad shader coverage or menu polish. If a route, weapon, or material is missing on a required fixture, implement it and rerun the affected match tests. Record unexpected scope by subsystem. Keep an open test visible until it has passed on the intended target.

## 8. Acceptance tests and evidence

| ID | Scenario | Passing observation |
| --- | --- | --- |
| A1 | Clean browser, bundled release | Click Play, obtain control, spawn on solid ground, and encounter a visible opponent. Browser network traffic contains only static application and authorized content files. |
| A2 | Navigation and input | Walk the recorded route, jump, traverse a stair or height change, collide with a wall, then pause while holding forward and fire. Resume stationary with no unintended firing. |
| A3 | Player offense | Collect a weapon during normal play. Miss once and hit once. Observe ammo, projectile or hit effect, actual damage, death, frag increment, and opponent respawn. |
| A4 | Opponent offense | Break line of sight and change position. The bot navigates to a new firing position, can kill the player, earns one frag, and can be fought again after player respawn. |
| A5 | Rules and presentation | Test item consumption and timed return, damage through armor, empty ammo, blocked hitscan, splash, and a world death or suicide. Cross-check HUD and event log against simulation state. |
| A6 | End and replay | Reach five frags by normal combat, show the correct winner, and restart. Also exercise a bot victory. The next match starts at zero with starting inventory and fresh pickups. |
| A7 | Original map | With licensed local archives, select q3dm1 in the shipping UI, navigate it, and complete A3, A4, and A6. Save map hash and local observations. Publish only evidence cleared for distribution. |
| A8 | Import and failure paths | Missing dependencies, invalid BSP, unsupported version, and corrupt PK3 yield clear recoverable errors. Cancelled import leaves the current match usable. Selected file contents stay on the device. |
| A9 | Delivery and responsiveness | Rebuild from documented inputs, serve the release directory, load the exact shipped Wasm, run the performance sequence, and verify source and license links. |

Use three independent forms of evidence. **Headless Rust tests** should replay seeded commands, assert state transitions and score invariants, and compare selected movements against the reference. **Browser integration tests** should start the shipping build, drive real keyboard and mouse events, and observe match events and UI state. A passive event log and a seeded test configuration are helpful. Mutating health, awarding frags through a test hook, teleporting the player, or calling the damage routine directly cannot satisfy A3, A4, or A6. **Human playtesting** checks whether a person can start the game, capture the mouse, aim under fire, hear feedback, finish a match, and start another. Include these steps in the handoff so a person can try the game. Record automated test results and human playtest feedback separately.

Preserve the build revision, asset hashes, commands, test seed where used, browser details, pass/fail results, and a short browser recording or equivalent timestamped sequence plus match log. Capture normal input, a pickup, each side scoring, intermission, and rematch. A screenshot of the arena proves rendering only. If hardware, licensed files, or a human tester are unavailable, finish the independent checks and label the specific missing observation. Report public-demo playability, original-map compatibility, and human acceptance independently.
